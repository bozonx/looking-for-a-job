# Как это работает

Ключевые механизмы, которые стоит понимать, чтобы настраивать систему и доверять её результатам.

## Общая схема

```
 скрипт сбора            агент                 npm run score          вы (UI)
 (фаза A)                (фаза B)              (детерминированно)
┌───────────┐         ┌──────────────┐        ┌──────────────┐      ┌──────────┐
│ лента     │──новые─▶│ частные      │──────▶│ overall,     │─────▶│ selected │
│ лимиты    │ scores: │ оценки, флаги│        │ region,      │      │ rejected │
│ предфильтр│  null   │ summary,     │        │ apply_target │      │ notes    │
│ дедуп     │         │ real_url     │        └──────────────┘      └──────────┘
└───────────┘         └──────────────┘
                              │
                              ▼
                       data/insights.md
```

Разделение ролей — главная идея: **скрипт** делает всё, что можно сделать без суждения (дёшево, воспроизводимо), **агент** — только то, где нужно понимание текста, **итоговое число** снова считает скрипт. Поэтому:
- токены тратятся только на новые вакансии, прошедшие предфильтр;
- поменяли предпочтения — пересчитали всё за секунду без LLM;
- оценки разных запусков и разных агентов сопоставимы.

Файлы — единственный источник истины. Ни базы, ни кэша, которому надо доверять: UI держит копию в памяти, но перечитывает файлы при изменениях.

## Сбор (фаза A)

`npm run collect` → общий конвейер `scripts/lib/collect.ts`; провайдер `scripts/providers/<источник>.ts` только отдаёт страницы списка и маппинг полей. Шаги:

1. **Индекс известных** — из всех файлов в `data/vacancies/`: по `id`, по всем URL (`source_url`, `real_url`, URL из `duplicates`), по `company+title`. Плюс `data/state/seen-<источник>.json`.
2. **Лента** — от новых к старым, постранично. Окно по дате — с прошлого полного сбора источника (−2 дня запаса, не дальше `COLLECT_MAX_AGE_DAYS`); вакансии вне окна пропускаются. Остановка при первом из условий: `COLLECT_STOP_ON_SEEN` известных/старых подряд (только с пагинацией, страница дочитывается; после обрыва — только по дате); `--limit` или `COLLECT_MAX_NEW`; `COLLECT_MAX_PAGES` страниц; конец ленты. Запросы повторяются при 429/5xx; 429 после повторов ставит хост на паузу (≥ 1 ч, `data/state/host-cooldown.json`), два 403 за запуск — пропуск хоста до конца запуска. См. [env.md](env.md).
3. **Предфильтр** (`config/prefilter.yaml`), без LLM:
   - заголовок содержит слово из `exclude_title` → отсеять (exclude важнее include);
   - иначе заголовок содержит слово из `include_title` **или** среди тегов есть `include_tags` → пропустить;
   - иначе → отсеять.
   Регистр не важен; «словные» ключи совпадают только с начала слова (`hr` не ловит `three`). Отсеянные записываются в лог с причиной и в `seen` (хранится 60 дней) — чтобы при следующем сборе считаться известными и не засорять лог.
4. **Дубль** (см. ниже; по `company+title` не сравниваются вакансии со скрытой компанией — «Confidencial», `Unknown`; в snapshot-источниках одноимённые вакансии одной компании с той же локацией — разные позиции, не склеиваются) → URL дописывается в `duplicates` существующей записи, пересчитывается `apply_target`. Повторно не скорится.
5. **Новая** → файл с фактами площадки, текстом (HTML→markdown) и `scores: null`.
6. **Лог** в `data/runs/<дата>-collect.md`, включая ошибки: сбой одной вакансии не прерывает сбор. В консоль — по строке на источник и «ИТОГ СБОРА» (подробный лог — только в файле; в `--dry-run` — в консоли).

Настройка предфильтра — баланс: слишком широкий → агент тратит токены на мусор (это видно по низким `fit` и записям `[scoring]` в журнале); слишком узкий → теряете вакансии (смотрите причины отсева в логе). После правки `prefilter.yaml` ранее отсеянное не пересмотрится, пока не удалить `data/state/seen-<источник>.json`.

## Дедупликация

`scripts/lib/dedupe.ts`. Ключи в порядке проверки:

1. **id** — та же вакансия с той же площадки.
2. **URL** — нормализованный: без `www`, `#…`, хвостового `/` и трекинговых параметров (`utm_*`, `ref`, `source`, `gh_src`…). Сравнивается со всеми URL записи, включая дубли и `real_url` — так ловятся копии на разных агрегаторах, ведущие в одну ATS.
3. **company + title** — нормализованные (кириллица транслитерируется): компания без `Inc/LLC/GmbH/…` и знаков, заголовок без `senior/junior/lead/remote/старший/ведущий/…` и скобок.

Ключ 3 может склеить разные вакансии (две позиции «Frontend Engineer» в одной компании). В пределах одного источника (разные id) это почти всегда одна роль в разных странах/офисах: такие склеиваются в одну запись — локации дописываются в `location`, ссылка (с `id`) — в `duplicates`, в логе раздел «Склеено». Для snapshot-источников запись считается открытой, пока в списке есть она или любая склеенная; между источниками склеивает с пометкой «совпадение только по названию, проверь». Агент сравнивает текст. Диагностика: `npm run dedupe -- --groups`, `--check`.

## Скоринг

### Двухуровневая схема

1. **Агент** ставит частные оценки 0–100 (`remote`, `startup`, `corporate`, `outsource`, `legitimacy`, `language`, `fit.*`), определяет `company_country` / `ru_speaking_team`, стоп-флаги и пишет обоснование. Методика — `playbooks/scoring.md`, поля — [vacancy-format.md](vacancy-format.md#оценки--scores).
2. **`npm run score`** (`scripts/lib/scoring.ts` + `rescore.ts`) считает итог по `config/weights.yaml`.

Агент не видит и не пишет `overall`. Это убирает соблазн «подогнать» итог и делает веса единственным рычагом.

### Формула

```
если есть стоп-флаг (STOP_FLAGS в scripts/lib/schema.ts) → overall = 0
иначе:
  overall = round( Σ wᵢ · vᵢ / Σ wᵢ )
  если лучший сырой fit (без веса трека) < fit_cap.below (40) → overall = min(overall, fit_cap.cap = 35)
```

где слагаемые:

| Группа | vᵢ | Пример весов |
|---|---|---|
| `positive` | оценка как есть | remote 3, fit 8, legitimacy 2, language 2, region 1, startup 1.5 |
| `inverse` | `100 − оценка` (чем выше, тем хуже) | corporate 2, outsource 0 (оценка ставится, но не влияет) |
| `fit` | `max` по трекам от `fit_tracks[трек] · fit[трек]` | vue 1, ai_engineer 1, fullstack 0.9, react 0.9, angular 0.8, automation 0.8 |

Детали, которые важны:
- Это **взвешенное среднее**, а не сумма: итог всегда 0–100, и абсолютный масштаб весов не важен — важны пропорции. `fit: 8` при сумме весов 19.5 значит, что fit даёт ~41 % балла.
- Вес `0` и оценка `null` выкидывают слагаемое **и из числителя, и из знаменателя**. Поэтому `region: null` не штрафует и не поощряет — просто не участвует.
- `fit` берёт **лучший** трек: вакансия хорошо подходит под одно резюме — этого достаточно. Вес трека < 1 (angular 0.8) понижает потолок: идеальный Angular даёт fit 80, а не 100. Вес 0 — трек игнорируется. Ограничение `fit_cap` сравнивает **сырой** fit: Angular с fit 45 — не «нерелевантная роль», хотя взвешенно это 36.
- `legitimacy < scam_legitimacy_below` (30) автоматически добавляет `scam` в `stop_flags`.

### Пример расчёта

Оценки: remote 95, startup 80, corporate 10, outsource 0, legitimacy 85, region 70 (europe), language 100, fit {vue 90, react 20, angular 0, fullstack 55, ai_engineer 70, automation 10}.

| Слагаемое | w | v | w·v |
|---|---|---|---|
| remote | 3 | 95 | 285 |
| legitimacy | 2 | 85 | 170 |
| fit (max: vue 1·90) | 8 | 90 | 720 |
| region | 1 | 70 | 70 |
| language | 2 | 100 | 200 |
| startup | 1.5 | 80 | 120 |
| corporate (inv) | 2 | 100−10 = 90 | 180 |
| outsource (inv) | 0 | — | пропуск (вес 0) |
| **Σ** | **19.5** | | **1745** |

overall = 1745 / 19.5 = 89.5 → **89**.

Та же вакансия, но «только гибрид в Берлине»: агент ставит `office_outside_ar` → overall = 0 независимо от остального.

### Что ещё делает `score`

Кроме `overall`, пересчитывает производные поля:
- `region` и `scores.region` — из `config/regions.yaml` по `company_country` / `ru_speaking_team` (справочник, а не суждение агента — чтобы одинаковые регионы всегда получали одинаковую оценку);
- `apply_method` — если был `unknown`, а `real_url` найден;
- `apply_target` — см. ниже;
- `stop_flags` — дополняется `scam`.

Результат проверяется строгой схемой; не прошедший проверку файл **не записывается** (ошибка в консоли / в UI).

### Как менять предпочтения

| Хочу | Что сделать |
|---|---|
| сильнее ценить удалёнку / слабее стартапы | веса в `weights.yaml → positive` |
| аутсорс — снова сделать минусом | `inverse.outsource` > 0 |
| перестать рассматривать трек | `fit_tracks.<трек>: 0` |
| поменять приоритет региона | `regions.yaml` |
| новый стоп-фактор | описать в `preferences.md` и `playbooks/scoring.md`, добавить в `weights.yaml → stop_flags` и в enum `STOP_FLAGS` в `scripts/lib/schema.ts`; уже отскоренные вакансии агенту придётся пересмотреть |
| поменять смысл частной оценки | `playbooks/scoring.md`, поднять `scoring_version`, перескорить агентом |

Потом — `npm run rescore` (или кнопка в UI). Всегда держите `preferences.md` (текст, читает агент) и `weights.yaml` (числа, читает скрипт) согласованными. Поднимайте `version` в `weights.yaml` при заметных изменениях — он печатается в выводе `score`.

Ориентир для порога отклика (`APPLY_SCORE_THRESHOLD=80`): после первых сотни вакансий посмотрите, где проходит граница между тем, что вы выбираете и отклоняете в UI, и подвиньте порог или веса.

## Выбор места отклика (`apply_target`)

`scripts/lib/target.ts`. Кандидаты: каналы `apply_channels` (`scripts/lib/channels.ts`: email → `email`, Telegram → `telegram`, WhatsApp, Facebook, личка `dm`, форма → `company-site`, ATS → `ats-<name>`, отклик на площадке → id площадки), `real_url`, `source`, все `duplicates`. `apply_method` — тип канала-победителя. Каждая ссылка классифицируется:
- домен известного агрегатора (remoteok, linkedin, wellfound, getonbrd, hh, himalayas, weworkremotely) → его id;
- домен известной ATS (greenhouse, lever, ashby, workable, smartrecruiters, …) → `ats-<name>`;
- любой другой → `company-site`.

Побеждает кандидат, стоящий выше в `config/source-priority.yaml`. Неизвестная списку ATS ранжируется как `ats-other`, но в поле пишется конкретное имя.

Зачем: отклик напрямую в ATS доходит до рекрутера надёжнее, чем через агрегатор, и снижает нагрузку на LinkedIn-аккаунт (риск блокировки). Поэтому агент при скоринге ищет `real_url` для интересных вакансий с агрегаторов.

## Журнал наблюдений

`data/insights.md` — общий журнал, который агент дописывает **на каждом сборе** (обязательный шаг playbook, даже если писать нечего: `- [none] <источник>: без замечаний`) и в будущем — при откликах.

Формат: заголовок-дата, по строке на наблюдение, с категорией и id вакансий.

```markdown
## 2026-11-13
- [gap] Kubernetes / Go control plane (remoteok-1137713) — нет в резюме
- [scoring] remoteok-1137713 прошёл предфильтр по «software engineer» — явно не по профилю
- [source] remoteok: у всех 4 вакансий apply_url ведёт на сам RemoteOK — real_url ищется вручную
```

| Категория | Что фиксирует | Куда переносить выводы |
|---|---|---|
| `gap` | требования, которых нет в резюме (особенно повторяющиеся) | учить / честно добавить в резюме, если опыт есть |
| `inadequate` | примеры неадекватного процесса | список примеров для стоп-фактора в `preferences.md` / `scoring.md` |
| `question` | новые вопросы форм | `profile/answers.md` |
| `scoring` | спорные и ошибочные оценки, промахи предфильтра | `playbooks/scoring.md`, `weights.yaml`, `prefilter.yaml` |
| `source` | особенности и проблемы площадок | `config/sources.md`, скрипт сбора |
| `none` | наблюдений нет | — |

Это петля обратной связи: система сама не меняет свои правила, она копит наблюдения, а решения принимаете вы. Просматривайте журнал раз в несколько дней; повторяющийся `gap` — сигнал для резюме, повторяющийся `scoring` про один и тот же тип вакансий — сигнал для предфильтра или весов.

## UI и конкурентная запись

Агент, скрипты и UI пишут в одни и те же файлы. Чтобы не терять правки:
- у каждого своя зона полей: UI — только `status` (`new`/`selected`/`rejected`), `starred`, `notes`; `score` — только производные поля; агент — остальное;
- UI перед записью перечитывает файл с диска и меняет только свои поля, запись атомарная (временный файл + rename);
- сервер следит за файлами (`chokidar`), браузер опрашивает API раз в 5 с; открытая карточка обновляется, несохранённые заметки не затираются.

Разбор/запись YAML — общий модуль `scripts/lib/vacancy.ts`, схема — общая `scripts/lib/schema.ts`.
