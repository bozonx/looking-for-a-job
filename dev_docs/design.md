# Дизайн-документ: система поиска работы с AI-агентом

Статус: v5 · 2026-11-16 · этапы 1 (сбор: открытые API и RSS/Atom-ленты) и 2 (UI) реализованы, этап 3 (отклик) — нет.

Как пользоваться и как устроено то, что уже есть, — в `docs/` (запуск, `.env`, формат вакансии, сбор, дедуп, скоринг, UI).
Здесь — цели, принципы, краткий итог сделанного и план.

## 1. Цель

Полуавтоматизировать поиск работы: агент по команде собирает новые вакансии, оценивает их по моим предпочтениям и сохраняет локально markdown-файлами. Я просматриваю их в локальном UI, отмечаю интересные и разбираю проблемные, после чего агент откликается на отмеченные и/или высоко оценённые вакансии, адаптируя резюме и сопроводительное письмо. Процесс заканчивается на отклике: переписку, тестовые и интервью веду сам.

## 2. Принципы

- **Файлы — источник истины.** Вакансии, требования, резюме, инструкции агенту — markdown. Без БД.
- **В git — только код, инструкции и обезличенные настройки.** `data/`, `profile/`, `.env` — в `.gitignore`; для приватных файлов есть `*.example.md`.
- **Агент-агностичность.** Любой агент читает `AGENTS.md` и по ключевой фразе выбирает playbook.
- **Человек в контуре.** Что агент не может решить уверенно — помечается для меня (`needs_attention`, `null` + обоснование), а не додумывается.
- **Локальность.** Всё на моём компьютере, в браузере Orca под моими аккаунтами; отклик идёт в видимом браузере.
- **Рутина — скриптам, суждения — агенту.** Загрузка, HTML→markdown, дедуп, итоговый балл, производные поля — детерминированные скрипты; агент ставит только частные оценки и факты. Дальше — анализ скриптом с прямым вызовом LLM API.

## 3. Три этапа

```
1. Сбор («собери»)  ──▶  2. Просмотр (UI)  ──▶  3. Отклик («откликнись»)
   скрипт + агент         Nuxt, я отмечаю        агент + браузер Orca
            └──────────── data/vacancies/*.md ────────────┘
```

## 4. Что сделано

**Этап 1 — сбор.** Подробно: `docs/how-it-works.md`, `playbooks/collect.md`, `playbooks/scoring.md`.

- Двухфазный сбор: скрипт `npm run collect` (общий конвейер `scripts/lib/collect.ts` + провайдеры `scripts/providers/`) — лимиты, предфильтр, дедуп, `seen`, запись, лог; затем агент скорит `npm run pending` в пределах `SCORE_MAX_PER_RUN`.
- Провайдеры (только открытые API и ленты, `config/sources.md`): **ATS компаний** (Greenhouse/Lever/Ashby — снимок открытых вакансий, пропавшие → `possibly_closed`), **Get on Board**, **HN Who is hiring**, **RemoteOK**, **Himalayas**, **Jobicy**, **Remotive**, стандартные ленты **RSS/Atom/JSON Feed** (We Work Remotely) — без кода, через `config/sources.yaml`. Новый источник = провайдер + строка в реестре + строка в `config/sources.md`.
- Скоринг: частные оценки агента + детерминированный `overall`, стоп-флаги, регион по справочнику, `apply_target` по `source-priority.yaml`; `npm run score` / `rescore` / `validate` (zod).
- Обслуживание: `cleanup` (закрытые — кроме ★; без решения — старше `CLEANUP_DEFAULT_DAYS`; автоматически после `collect`, если `CLEANUP_ON_COLLECT`), `dedupe` (диагностика), `fetch-page` (HTML → markdown), журнал `data/insights.md`.
- Обратная связь: `resume_match` в каждой вакансии (сравнение с резюме, словарь `config/skills.yaml`), метрики прогонов `data/runs/stats.jsonl`, отчёт `npm run insights`, разбор — `playbooks/analyze.md`.

**Этап 2 — UI** (`app/`, Nuxt SPA + Nitro). Подробно: `docs/running.md`, раздел «UI».

- Кэш вакансий в памяти + `chokidar`, опрос раз в 5 с, ошибки разбора видны в UI.
- Вкладки, фильтры, сортировка, карточка, горячие клавиши, rescore из UI.
- Запись только `status` (`null`/`selected`), `starred`, `flagged`, `notes` — с перечитыванием файла и атомарной записью.

## 5. Что предстоит

### 5.1. Источники (ближайшее)

Порядок — от безопасных API к рискованным площадкам:

Подключены: Get on Board, HN, Himalayas, We Work Remotely, Jobicy, Remotive, Greenhouse/Lever/Ashby (см. §4).

1. **Пополнение списка компаний ATS** — из компаний, найденных на агрегаторах с высоким `overall`.
2. **hh.ru** — анонимный API закрыт (403), нужна регистрация приложения с модерацией; отложено.
3. **LinkedIn** — только после стабилизации конвейера: HTML через браузер Orca (`fetch-page.ts`), умеренные объёмы, паузы.

Для HTML-источников нужно добавить в конвейер загрузку через Orca (сейчас провайдеры только `fetch`). Пагинация (`COLLECT_MAX_PAGES`) впервые заработает именно на них.

### 5.2. Этап 3 — отклик («откликнись»)

Не реализован: нет `playbooks/apply.md`, `playbooks/tailor.md`, `scripts/render-resume.ts`; переменные `APPLY_*`, `LINKEDIN_APPLY_MAX_PER_DAY`, `TYPE_DELAY_MS` зарезервированы (`docs/env.md`). При реализации — добавить маршрут в `AGENTS.md`.

**Команды:**

| Фраза | Набор вакансий |
|---|---|
| «откликнись» | оба набора сразу: `selected` ∪ (`status: null` и `overall ≥ APPLY_SCORE_THRESHOLD`) |
| «откликнись выбранным» | только `selected` |
| «откликнись по скорингу» | только по порогу: `status: null` и `overall ≥ APPLY_SCORE_THRESHOLD` |
| «повтори отклики» | `needs_attention` + `apply_failed` — повтор с обновлёнными `answers.md` / медиа |

**Алгоритм:**

1. `npm run check-alive` по набору (закрытые не откликаем). Сформировать список: без `possibly_closed`, без ⚑, с учётом `APPLY_MAX_PER_RUN` и `LINKEDIN_APPLY_MAX_PER_DAY`. Отобранные только по скорингу — показать и ждать подтверждения (`APPLY_CONFIRM_SCORED`); `selected` — без подтверждения.
2. Предпроверка (по тексту вакансии или открыв форму, но не отправляя): нестандартные медиа-требования → `needs_attention: special_media`; вопросы формы, на которые нет ответа в `about.md` / `answers.md` → `needs_attention: unknown_question` с полным текстом. Стандартные видео/аудио-визитки — из `profile/media/`.
3. Адаптировать резюме и письмо, сгенерировать PDF в `data/generated/<id>/`.
4. Открыть `apply_target` (fallback: `real_url` → `source_url`), заполнить, приложить, отправить.
5. `status: applied`, `applied_at`, `apply_log`; отчёт в `data/runs/<date>-apply.md` (что отправлено, ответы, резюме, по возможности скриншот).
6. Любая неуверенность (капча, логин, странная форма, противоречие) — стоп по этой вакансии, `needs_attention` с описанием, к следующей. Техническая ошибка — `apply_failed`.

**Адаптация (`tailor.md`):**

- База — `best_resume` из `profile/resumes/`; переставить акценты, подобрать формулировки и ключевые слова вакансии под ATS.
- **Граница:** переформулировать, переупорядочивать, опускать и подсвечивать только то, что уже есть в резюме/`about.md`. Не добавлять технологии, годы, должности, проекты, которых нет; отсутствующие ключевые слова не вписывать.
- Письмо — по `profile/cover-letter.md`, на языке вакансии.
- PDF — `render-resume.ts`: markdown → HTML-шаблон → PDF через Playwright/Chromium; один столбец, текстовый слой, без таблиц и картинок.

**«Человеческий» темп:** случайные паузы между вакансиями (`APPLY_DELAY_MIN_SEC`…`MAX`), посимвольный ввод (`TYPE_DELAY_MS`).

### 5.3. Мелкие доработки

- Проверка типов `.vue`-файлов — когда `vue-tsc` станет совместим с TypeScript 7.
- Поиск `real_url` для вакансий с агрегаторов — сейчас вручную агентом; можно автоматически сверять с ATS-провайдером, если компания есть в `config/sources.yaml`.

### Жизненный цикл вакансии

1. `collect` сохраняет вакансию с `collected_run` — вкладка «Новые» в UI = вакансии последнего запуска сбора.
2. Пользователь отмечает только нужное: «Откликнуться» (`selected`), ⚑ «Проблемная» (`flagged`, причина — в `notes`),
   ★ (`starred`) — личная пометка «не потерять», ни на что, кроме защиты от чистки, не влияет. Неотмеченное = неинтересное.
3. Автоотклик (этап 3): `selected` и/или вакансии по порогу скоринга → `applied` / `needs_attention` / `apply_failed`.
4. «проверь проблемные» (`playbooks/flagged.md`): агент исправляет скоринг/данные, записывает разбор в `data/flagged-cases.md`
   и снимает ⚑; дальше вакансия живёт по общим правилам.
5. Чистка после каждого сбора: закрытые (`possibly_closed`) — сразу, кроме ★; без статуса/★/⚑ — старше `CLEANUP_DEFAULT_DAYS`.
   Закрытость выясняют `collect` (вакансия пропала из снимка ATS) и `check-alive` (404/410/«not found» по real_url).

## 6. Риски

- **LinkedIn и блокировки.** Банят в основном за объёмы и ритм. При сборе — лимиты и паузы; при отклике — приоритет откликов вне LinkedIn через `apply_target`. Easy Apply без альтернатив — `apply_method: easy-apply`, вручную или агентом в пределах `LINKEDIN_APPLY_MAX_PER_DAY=5` (по `applied_at` за сутки; первую неделю можно 3).
- **Детект автоматизации.** Медленный ввод помогает только против простых эвристик; основное — реальный браузер Orca с моим профилем.
- **Выдумывание фактов** — граница адаптации и правило «не знаешь — `needs_attention`».
- **Стоимость токенов** — предфильтр, HTML→markdown скриптом, дубли без повторного скоринга, лимит `SCORE_MAX_PER_RUN`, источники с API.
- **Разные агенты** — нейтральные playbooks, специфика — адаптером в `AGENTS.md`.
- **ToS площадок** запрещают автоматизацию; риск — блокировка аккаунта, принимается осознанно.

## 7. Принятые решения

- Стоп-факторы и шкалы — `config/weights.yaml`, `config/preferences.md`; EOR и аутстаф допустимы и не штрафуются.
- `COLLECT_STOP_ON_SEEN=5`; `LINKEDIN_APPLY_MAX_PER_DAY=5`.
- Подтверждение списка отклика — только для вакансий, отобранных по скорингу.
- UI без SSR и без отдельной библиотеки front matter — общий модуль со скриптами.
