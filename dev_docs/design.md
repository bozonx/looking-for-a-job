# Дизайн-документ: система поиска работы с AI-агентом

Статус: черновик · Дата: 2026-11-13

## 1. Цель

Полуавтоматизировать поиск работы: агент ежедневно собирает вакансии, оценивает их по моим требованиям и сохраняет в репозиторий в виде markdown-файлов. Я просматриваю результаты в локальном UI, отмечаю интересные, после чего агент откликается на отмеченные и/или высоко оценённые вакансии.

Ключевые принципы:

- **Файлы — источник истины.** Вакансии, требования, резюме и инструкции агенту — это markdown в git. Без базы данных.
- **Агент-агностичность.** Любой агент (Claude Code, Codex и т.д.) запускается из корня репозитория, читает `AGENTS.md` и по ключевому слову выбирает нужный сценарий (playbook).
- **Человек в контуре.** Агент собирает и предлагает; решения о приоритете принимаю я (за исключением автоотклика по порогу скоринга, который включается явно).
- **Локальность.** Всё работает на моём компьютере, в моём браузере, под моими аккаунтами.

## 2. Обзор: три этапа

```
┌──────────────┐     ┌───────────────────┐     ┌──────────────────┐
│ 1. Сбор      │ ──▶ │ 2. Просмотр (UI)  │ ──▶ │ 3. Отклик        │
│ агент        │     │ Nuxt + Nitro      │     │ агент            │
│ «собери»     │     │ я отмечаю         │     │ «откликнись»     │
└──────────────┘     └───────────────────┘     └──────────────────┘
        │                     │                         │
        └──────────── vacancies/*.md (front matter) ────┘
```

| Этап | Кто запускает | Чем | Результат |
|---|---|---|---|
| 1. Сбор | я, через агента, ежедневно | агент + браузер (Chromium в Orca) | новые `vacancies/*.md` со скорингом |
| 2. Просмотр | я | `npm run dev` → Nuxt UI | `status: selected` / `rejected` в front matter |
| 3. Отклик | я, через агента | агент + браузер | заполненные формы, `status: applied`, лог отклика |

│   ├── requirements.md        # требования к вакансии (удалёнка, не корпорация, ...)
│   ├── about.md               # факты обо мне: контакты, локация, зарплата, визы, языки
│   ├── answers.md             # заготовленные ответы на типовые вопросы форм

│       ├── angular.md
│       ├── fullstack.md

│       (+ PDF-версии для загрузки в формы)

## 4. Формат вакансии

Один файл = одна вакансия. Тело — оригинальный текст (очищенный из HTML в markdown), front matter — всё, что посчитал агент.

```yaml
---
id: linkedin-4012345678            # источник + внешний id, ключ дедупликации
title: Senior Vue.js Developer
company: Acme AI
source: linkedin
source_url: https://www.linkedin.com/jobs/view/4012345678
real_url: https://jobs.ashbyhq.com/acme/abc   # прямая ссылка после редиректов, если нашлась
apply_method: ats-ashby            # easy-apply | ats-<name> | email | external | unknown
collected_at: 2026-11-13
posted_at: 2026-11-12
location: Remote (EU)
salary: { min: 5000, max: 7000, currency: USD, period: month }
employment: contract               # full-time | contract | b2b | unknown
languages: [en]

summary: >
  Стартап на seed-стадии, AI-ассистент для юристов. Нужен фронтенд на Vue 3 + Nuxt,
  будет касаться LLM-интеграций.
key_points:
  - Vue 3, Nuxt, TypeScript
  - Работа с LLM API
  - Таймзона CET ±3
red_flags:
  - Не указана зарплата

scores:                            # 0–100
  remote: 95
  startup: 80
  not_corporate: 90                # нет признаков крупного бизнеса / жёсткого оформления
  legitimacy: 85                   # обратное к «фейковости»
  fit:
    vue: 90
    react: 20
    angular: 0
    fullstack: 55
    ai_engineer: 70
  overall: 84
best_resume: vue
score_reasoning: >
  Явно указана полная удалёнка, команда 8 человек, ссылка на сайт и Crunchbase ...

status: new                        # new | selected | rejected | applied | apply_failed | archived
starred: false
notes: ""                          # мои заметки из UI
applied_at: null
apply_log: null
scoring_version: 1                 # версия методики, чтобы можно было пересчитать
---

<оригинальный текст вакансии>
```

## 5. Этап 1 — Сбор («собери»)

Алгоритм из `playbooks/collect.md`:

1. Прочитать `sources/sources.md`, `profile/requirements.md`, `playbooks/scoring.md`.
2. Построить индекс уже собранных вакансий (id + нормализованные `company+title`) для дедупликации.
3. Для каждого источника:
   1. Открыть URL списка с заранее настроенными фильтрами (в браузере Orca, под моей сессией, если нужна авторизация).
   2. Прочитать **одну страницу** последних вакансий.
   3. По заголовку/компании/локации отсеять очевидно нерелевантное (дешёвый предфильтр).
   4. Для прошедших — открыть страницу вакансии, забрать текст, пройти по кнопке «Apply» и попытаться найти **реальную ссылку** (ATS компании, сайт), не отправляя ничего.
   5. Оценить по методике, записать markdown-файл.
4. Записать лог запуска в `runs/`: сколько просмотрено, отсеяно по заголовку, сохранено, ошибки (капча, разлогин).

## 6. Этап 2 — Просмотр (UI)

**Стек:** Nuxt 3/4 + Nitro, локальный запуск.

- **Бэкенд (Nitro):** при старте читает все `vacancies/**/*.md` (`gray-matter`) в память; `chokidar` следит за изменениями — так новые вакансии от агента появляются без перезапуска.
  - `GET /api/vacancies` — список (только front matter), фильтры/сортировка.
  - `GET /api/vacancies/:id` — полный файл.
  - `PATCH /api/vacancies/:id` — изменение `status`, `starred`, `notes`; запись обратно в front matter с сохранением тела.
- **Фронт:**
  - Таблица: заголовок, компания, дата, overall, скоринг-бейджи (remote/startup/legitimacy), лучший профиль, статус.
  - Фильтры: статус, минимальный overall, профиль резюме, источник, дата.
  - Карточка: summary, key_points, red_flags, обоснование скоринга, ссылки (source/real), раскрывающийся оригинальный текст.
  - Быстрые действия с клавиатуры: отметить «откликнуться» / «отклонить» / следующая.

## 7. Этап 3 — Отклик («откликнись»)

Команды:

| Фраза | Набор вакансий |
|---|---|
| «откликнись» / «ответь» | `status: selected` **∪** `scores.overall ≥ APPLY_SCORE_THRESHOLD` (и `status: new`) |
| «откликнись выбранным» | только `status: selected` |
| «откликнись по скорингу» | только по порогу |

Алгоритм (`playbooks/apply.md`):

1. Сформировать список, показать мне его и **дождаться подтверждения** (как минимум для пакета по скорингу).
2. Для каждой: открыть `real_url` (или `source_url`), выбрать резюме `best_resume`, заполнить форму по `profile/about.md` и `profile/answers.md`, при необходимости сгенерировать сопроводительное письмо.
3. Неизвестные вопросы формы — не выдумывать: пропустить вакансию с `status: apply_failed` и записать вопрос в `apply_log`, чтобы я дополнил `answers.md`.
4. После отправки — `status: applied`, `applied_at`, скриншот/текст отправленного в `runs/`.

`.env`:

```
APPLY_SCORE_THRESHOLD=80
APPLY_MAX_PER_RUN=15
APPLY_REQUIRE_CONFIRMATION=true
COLLECT_PAGES_PER_SOURCE=1
```

## 8. Скоринг

- Критерии и веса описаны текстом в `profile/requirements.md`, методика — в `playbooks/scoring.md`.
- Агент выставляет частные оценки 0–100 с коротким обоснованием; `overall` вычисляется **детерминированно** по весам (скрипт или формула в playbook), чтобы не зависеть от «настроения» модели.
- Жёсткие стоп-факторы (не удалёнка, требуется релокация, явный скам) обнуляют `overall` независимо от остального.
- `scoring_version` позволяет пересчитать старые вакансии при изменении требований.

## 9. Технологии

| Задача | Выбор | Комментарий |
|---|---|---|
| Хранилище | markdown + YAML front matter в git | история изменений бесплатно |
| Агент | Claude Code / Codex | вход через `AGENTS.md` |
| Браузер | Chromium в Orca (`orca` CLI) | мои сессии, куки, авторизация |
| UI | Nuxt + Nitro, `gray-matter`, `chokidar` | всё в памяти |
| Валидация front matter | `zod`-схема, общая для UI и скрипта проверки | агент запускает `npm run validate` после записи |

## 10. Вопросы крупного плана

### Идея и процесс

1. **Риск блокировки аккаунтов.** LinkedIn и подобные активно детектят автоматизацию, особенно массовые отклики. Потеря основного LinkedIn-аккаунта во время поиска работы — критичный сценарий. Готов ли ты к этому риску, или для LinkedIn ограничиваемся только чтением/сбором, а отклик делается через ATS компании (`real_url`)? Нужны ли лимиты темпа и «человеческие» паузы?
2. **Автоотклик без просмотра.** Отклик по скорингу означает, что от твоего имени уйдут заявки, которые ты не видел. Ошибка скоринга = неловкий отклик в компанию, куда ты, возможно, захочешь податься позже нормально. Нужен ли обязательный этап подтверждения списка, или хотя бы «сухой прогон» на первые недели?
3. **Одна страница в день — достаточно ли?** На популярных площадках за сутки выходит больше одной страницы под фильтром; на нишевых — меньше. Может, стоит ориентироваться не на «одну страницу», а на «до последней уже виденной вакансии» (инкрементальный сбор)?
4. **Что после отклика?** Документ заканчивается на отправке формы. Но дальше — ответы рекрутеров, тестовые, интервью, отказы. Нужен ли этап 4 (трекинг воронки: письма в почте, статусы `interview`/`offer`/`rejected_by_company`) и аналитика, какие профили/источники реально конвертируются? Без обратной связи скоринг невозможно калибровать.
5. **Калибровка скоринга.** Как понять, что оценки «remote 85» или «startup 70» что-то значат? Предлагаю, чтобы твои ручные решения в UI (selected/rejected) сохранялись и периодически использовались агентом для уточнения `requirements.md`. Нужно ли это?
6. **Дубли между площадками.** Одна и та же вакансия встречается на LinkedIn, Wellfound, сайте компании и в агрегаторах. Достаточно ли дедупликации по `company + title`, и куда откликаться при дубле — в первоисточник?
7. **Сопроводительные письма и адаптация резюме.** Пять фиксированных резюме или агент должен подстраивать резюме/письмо под конкретную вакансию? Последнее сильно повышает конверсию, но и риск выдумывания фактов — нужна граница «что агенту можно перефразировать, а что нельзя».
8. **Правдивость ответов в формах.** Вопросы вроде «сколько лет опыта с X», «готовы ли к релокации», «нужна ли виза», ожидаемая зарплата — агент не должен импровизировать. Готов ли ты вести `answers.md` как полный справочник и пополнять его после каждого `apply_failed`?
9. **Противоречие «стартап» vs «не корпорация / без официального оформления».** Что именно является целью: формат оплаты (контракт/B2B), размер компании, культура? Некоторые стартапы требуют full-time employment через EOR (Deel, Remote.com) — это подходит или нет? От ответа зависит, это один критерий или два разных.
10. **Персональные данные в git.** Резюме, контакты, ответы о зарплате и визах будут лежать в репозитории. Он только локальный или будет пушиться на GitHub? Если пушится — `profile/` нужно держать вне git или в приватном отдельном репо.
11. **Удалённые/закрытые вакансии.** Ссылки протухают. Хранить ли снимок HTML/скриншот, и как помечать вакансии, которые закрылись до отклика (`archived`, автоочистка по возрасту)?

### Инструменты и технологии

12. **Агент как «краулер» — дорого и нестабильно.** Прогон LLM-агента через браузер по каждой вакансии — это много токенов и разная детерминированность от запуска к запуску. Альтернатива: детерминированный скрипт (Playwright, подключённый к тому же Chromium через CDP) собирает списки и тексты, а агент только оценивает и пишет front matter. Гибрид: скрипт для источников с открытыми данными/API (Greenhouse, Lever, Ashby, RemoteOK, HN «Who is hiring» имеют JSON), агент + браузер — только для LinkedIn и сложных сайтов. Какой вариант тебе ближе?
13. **Разные агенты — разное поведение.** Claude и Codex по-разному управляют браузером (Orca CLI, MCP, Computer Use), и один и тот же playbook может работать у одного и ломаться у другого. Держим ли мы playbook нейтральным (только «что сделать») с адаптерами под агента, или выбираем одного основного агента?
14. **Браузер Orca как зависимость.** Весь сбор и отклик завязан на встроенный браузер Orca и его CLI. Если нужно запускать из другого окружения (по расписанию, в фоне, на сервере) — это не сработает. Нужен ли запуск без участия человека (cron), или «я сам запускаю каждый день» — осознанное ограничение?
15. **Капчи, 2FA, разлогин.** Что агент делает, когда упирается в капчу или просьбу войти — ждёт тебя, пропускает источник, шлёт уведомление?
16. **Файлы vs база.** Markdown в git отлично подходит для сотен вакансий, но при тысячах и частых правках статусов из UI получится шумная git-история и конфликты при одновременной работе агента и UI. Стоит ли разделить: текст и скоринг агента — в `.md`, а мои пользовательские статусы/заметки — в отдельном `state.json` (или SQLite)? Коммитить ли вакансии вообще?
17. **Детерминированность скоринга.** Должен ли `overall` считаться кодом из частных оценок (воспроизводимо, легко менять веса и пересчитывать в UI), или агент ставит итог целиком? Предлагаю первое — и тогда веса лучше держать в конфиге, а не в тексте.
18. **Скоринг на дешёвой модели.** Предфильтр по заголовкам и полный скоринг можно отдавать разным моделям (дешёвая/быстрая для фильтра, сильная для анализа). Нужно ли управление выбором модели, или агент один на всё?
19. **Юридическая сторона.** Пользовательские соглашения LinkedIn и ряда площадок запрещают скрейпинг и автоматизированные действия. Для личного использования риск в основном — блокировка аккаунта (см. п. 1), но стоит это зафиксировать осознанно.
