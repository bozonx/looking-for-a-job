# Дизайн-документ: система поиска работы с AI-агентом

Статус: черновик v4 (этап 1 реализован для RemoteOK; конвейер сбора общий для провайдеров, этап 2 — UI — реализован, этап 3 — нет) · Дата: 2026-11-16

Пользовательская документация (запуск, первый старт, формат вакансии, `.env`, устройство скоринга) — в `docs/`.

## 1. Цель

Полуавтоматизировать поиск работы: агент по моей команде собирает новые вакансии, оценивает их по моим предпочтениям и сохраняет локально в виде markdown-файлов. Я просматриваю результаты в локальном UI, отмечаю интересные и разбираю проблемные, после чего агент откликается на отмеченные и/или высоко оценённые вакансии, адаптируя резюме и сопроводительное письмо.

Ключевые принципы:

- **Файлы — источник истины.** Вакансии, требования, резюме и инструкции агенту — это markdown. Без базы данных.
- **В git — только код, инструкции и обезличенные настройки.** Вакансии, логи, сгенерированные PDF и персональные данные лежат локально и находятся в `.gitignore`.
- **Агент-агностичность.** Любой агент (Claude Code, Codex и т.д.) запускается из корня репозитория, читает `AGENTS.md` и по ключевой фразе выбирает нужный сценарий (playbook).
- **Человек в контуре.** Агент собирает и предлагает; всё, что он не может решить уверенно, помечается для меня, а не додумывается.
- **Локальность.** Всё работает на моём компьютере, в браузере Orca, под моими аккаунтами. Процесс отклика идёт в видимом браузере, я могу за ним наблюдать.
- **MVP — через агента, потом — скрипты + LLM API.** Сначала всё делает агент; рутину (загрузка страницы, HTML→markdown, дедупликация, расчёт итогового балла) выносим в скрипты, чтобы экономить токены. После MVP — возможность прогонять анализ скриптом, напрямую вызывающим LLM.

## 2. Обзор: три этапа

```
┌──────────────┐     ┌───────────────────┐     ┌──────────────────┐
│ 1. Сбор      │ ──▶ │ 2. Просмотр (UI)  │ ──▶ │ 3. Отклик        │
│ агент        │     │ Nuxt + Nitro      │     │ агент            │
│ «собери»     │     │ я отмечаю/разбираю│     │ «откликнись»     │
└──────────────┘     └───────────────────┘     └──────────────────┘
        │                     │                         │
        └────────── data/vacancies/*.md (front matter) ─┘
```

| Этап | Кто запускает | Чем | Результат |
|---|---|---|---|
| 1. Сбор | я, через агента, обычно раз в день | агент + браузер Orca + скрипты | новые `vacancies/*.md` со скорингом, связанные дубли |
| 2. Просмотр | я | `npm run dev` → Nuxt UI | `status: selected` / `rejected`, разбор `needs_attention` |
| 3. Отклик | я, через агента | агент + браузер Orca | адаптированные резюме/письма, заполненные формы, `status: applied` |

Процесс заканчивается на отклике. Переписку с рекрутерами, тестовые и интервью я веду сам (трекинг воронки — вне MVP).

## 4. Формат вакансии

Один файл = одна вакансия (одна «каноническая» запись на группу дублей, см. §5.3). Тело — оригинальный текст (HTML → markdown), front matter — всё, что посчитал агент.

```yaml
---
id: linkedin-4012345678            # источник + внешний id
title: Senior Vue.js Developer
company: Acme AI
company_country: DE                # страна компании-работодателя, если известна
source: linkedin
source_url: https://www.linkedin.com/jobs/view/4012345678
real_url: https://jobs.ashbyhq.com/acme/abc   # прямая ссылка после редиректов, если нашлась
apply_method: ats-ashby            # easy-apply | ats-<name> | email | comment | external | unknown
duplicates:                        # та же вакансия на других площадках
  - { source: wellfound, url: https://wellfound.com/jobs/..., seen_at: 2026-11-13 }
  - { source: company-site, url: https://acme.ai/careers/vue }
apply_target: ats-ashby            # место отклика: вычисляет скрипт по source-priority.yaml (§5.3)
collected_at: 2026-11-13
posted_at: 2026-11-12
location: Remote (EU)
region: europe                     # НЕ агент: группа из regions.yaml по company_country / ru_speaking_team
salary: { min: 5000, max: 7000, currency: USD, period: month }
employment: contract               # full-time | contract | b2b | eor | unknown
vacancy_language: en               # язык, на котором написан текст вакансии
work_languages: [en]               # требуемый язык общения; пусто/null, если не указан явно
role_tracks: [vue, ai_engineer]    # к каким направлениям относится
tags: [vue, nuxt, typescript]      # теги площадки как есть (если отдаёт); для предфильтра и поиска

summary: >
  Стартап на seed-стадии, AI-ассистент для юристов. Нужен фронтенд на Vue 3 + Nuxt,
  будет касаться LLM-интеграций.
key_points:
  - Vue 3, Nuxt, TypeScript
  - Работа с LLM API
  - Таймзона CET ±3
red_flags:
  - Не указана зарплата

scores:                            # 0–100, точность до единицы не важна (шаг 5–10)
  remote: 95                       # насколько работа реально удалённая
  startup: 80                      # признаки стартапа
  corporate: 10                    # крупный бизнес у НАНИМАЮЩЕЙ стороны (см. §8.2)
  outsource: 0                     # аутсорс/аутстаф-компания
  end_client_corporate: null       # для аутсорса: крупный ли конечный клиент; иначе null
  legitimacy: 85                   # обратное к «фейковости»/скаму
  region: 70                       # НЕ агент: score.ts берёт из regions.yaml
  language: 100                    # насколько подходит язык общения (ru/en/es)
  fit:                             # соответствие направлениям/резюме
    vue: 90
    react: 20
    angular: 0
    fullstack: 55
    ai_engineer: 70
  overall: 84                      # считается скриптом score.ts, не агентом
stop_flags: []                     # office_outside_ar | location_restricted | nationality_excluded | ru_corporate | inadequate | scam (§8.1)
best_resume: vue
score_reasoning: >
  Явно указана полная удалёнка, команда 8 человек, ссылка на сайт и Crunchbase ...

requirements_special:              # нестандартные требования отклика
  - { type: video, standard: false, details: "Видео 2 мин: расскажите о проекте с LLM и назовите кодовое слово BLUE" }

status: new                        # см. жизненный цикл ниже
attention_reason: null             # почему нужен я: unknown_question | special_media | captcha | login | ambiguous | other
attention_details: null            # конкретика: текст вопроса, что не получилось
starred: false
notes: ""                          # мои заметки из UI
possibly_closed: false             # агент увидел, что вакансия закрыта (ненадёжный признак)
applied_at: null
apply_log: null                    # ссылка на data/runs/... и краткий итог
scoring_version: 1
---

<оригинальный текст вакансии>
```

**Жизненный цикл `status`:**

```
new ──▶ selected ──▶ applied
 │          │   └──▶ needs_attention ──(я дополнил answers.md / разобрался)──▶ selected / applied
 │          └──────▶ apply_failed  (техническая ошибка — можно повторить)
 └──▶ rejected
```

`needs_attention` — вакансия требует моего решения (неизвестный вопрос формы, нестандартное видео/голосовое, неоднозначность и т.п.). UI показывает их отдельным списком с `attention_reason` / `attention_details`.

## 5. Этап 1 — Сбор («собери»)

### 5.1. Ограничения обхода (настраиваются в `.env`)

Для каждого источника листаем список (отсортированный по дате) и останавливаемся при **первом** из условий:

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `COLLECT_MAX_PAGES` | 5 | не более N страниц пагинации (у RemoteOK пагинации нет — не применяется) |
| `COLLECT_MAX_AGE_DAYS` | 7 | дошли до вакансий старше N дней |
| `COLLECT_STOP_ON_SEEN` | 5 | встретили подряд N уже известных вакансий (одна «старая» не повод останавливаться: площадки поднимают промо-вакансии наверх). «Известные» — сохранённые **и** ранее отсеянные предфильтром (`data/state/seen-<source>.json`, хранятся 60 дней) |

Так сбор получается инкрементальным: запускаю когда хочу, агент добирает только новое в пределах лимитов.

### 5.2. Алгоритм (`playbooks/collect.md`)

Сбор **двухфазный**: рутину делает скрипт, агент тратит токены только на новые вакансии.

**Фаза A — скрипт** `npm run collect` (все источники из `scripts/providers/index.ts`; один — `npm run collect -- <source>`). Общий конвейер — `scripts/lib/collect.ts`; провайдер (`scripts/providers/<source>.ts`) только загружает страницы списка (`fetchPage`) и переводит вакансию площадки в поля front matter (`build`). Новый источник = провайдер + строка в реестре + строка в `config/sources.md`.

1. Построить индекс известных вакансий (id, нормализованные URL, включая `duplicates`, `company+title`) и загрузить `seen`.
2. Забрать список постранично (API/JSON — `fetch` с повторами при 429/5xx и паузой между страницами; HTML-площадки — через браузер Orca + `fetch-page.ts`), пройти его с остановкой по §5.1.
3. **Предфильтр** по `config/prefilter.yaml` (заголовок/теги). Отсеянное — в лог запуска и в `seen`.
4. Дубль по индексу → дописать в `duplicates` существующей записи, пересчитать `apply_target`, не скорить повторно; id дубля — в `seen`. Совпадение только по `company+title` **в том же источнике** с другим id считается разными вакансиями: сохраняется отдельно и попадает в лог как «возможный дубль». Ключи нормализуются с транслитерацией кириллицы.
5. Новую — сохранить с текстом (HTML → markdown), фактами из площадки и `scores: null`.
6. Лог запуска в `data/runs/`: страниц / в ленте / просмотрено / отсеяно / известных / дублей / сохранено, причина остановки, ошибки. Ошибка отдельной вакансии не прерывает сбор; ошибка загрузки списка останавливает только этот источник (код выхода 1).

**Фаза B — агент:**

1. `npm run pending` → для каждой новой: частные оценки, summary, флаги, `requirements_special` по `playbooks/scoring.md`.
2. Если отклик ведёт на агрегатор — поискать **реальную ссылку** (сайт компании / ATS), ничего не отправляя → `real_url`.
3. `npm run score` (overall, `scores.region`, `apply_method`, `apply_target`) → `npm run validate`.
4. Дописать `data/insights.md` (§8.5) и кратко отчитаться.

### 5.3. Дубли и выбор места отклика

- Ключи совпадения: внешний id; `real_url`; нормализованные `company + title` (+ близость текста, если есть сомнения — агент решает, совпадает ли).
- Все найденные копии записываются в `duplicates` одной канонической записи.
- `apply_target` вычисляет скрипт (`scripts/lib/target.ts`; при сборе, при добавлении дубля и в `npm run score`) среди `real_url`, источника и всех дублей по `config/source-priority.yaml`; ATS, которой нет в списке, ранжируется как `ats-other`, а в поле пишется конкретное `ats-<name>`. Порядок, например: `company-site / ATS (greenhouse, lever, ashby, workable)` > нишевые площадки (Wellfound, Get on Board, hh.ru) > агрегаторы > LinkedIn. Это одновременно снижает нагрузку на LinkedIn-аккаунт (см. §11).
- При сборе агент может целенаправленно поискать вакансию с LinkedIn на сайте компании / в её ATS, чтобы получить альтернативное место отклика.

### 5.4. Закрытые вакансии

Специально не отслеживаем: цель — подаваться в тот же день или ближайший рабочий. Если агент случайно увидел, что вакансия закрыта, — ставит `possibly_closed: true` (ненадёжный признак). При отклике закрытые отсеиваются по факту. Очистка — скриптом `npm run cleanup -- [--older-than 30d] [--status rejected,applied] [--dry-run]` (возраст по `collected_at`, по умолчанию `CLEANUP_DEFAULT_DAYS`; со звездой не удаляются); без запуска вакансии копятся.

## 6. Этап 2 — Просмотр (UI)

**Стек:** Nuxt + Nitro (SPA, `ssr: false`), локальный запуск: `npm run dev` → http://localhost:3000; сборка — `npm run ui:build`. Разбор и запись файлов — общий со скриптами модуль `scripts/lib/vacancy.ts` (`yaml`), а не отдельная библиотека.

- **Бэкенд (Nitro):** при старте читает все `data/vacancies/**/*.md` в память; `chokidar` следит за изменениями. Файлы, которые не удалось разобрать, не пропадают молча: список с ошибками отдаётся вместе с вакансиями и показывается в UI.
  - `GET /api/vacancies` — все вакансии (только front matter) + ошибки разбора. Фильтрация и сортировка — на клиенте (вакансий десятки–сотни).
  - `GET /api/vacancies/:id` — полный файл.
  - `PATCH /api/vacancies/:id` — только `starred`, `notes` и `status` ∈ `new | selected | rejected` (`needs_attention`, `applied`, `apply_failed` ставит агент). Перед записью файл перечитывается с диска, чтобы не затереть правки агента; запись атомарная (временный файл + rename).
  - `POST /api/rescore` — то же, что `npm run rescore` (общая функция `scripts/lib/rescore.ts`): пересчёт производных полей (`scores.region`, `apply_method`, `apply_target`, `scores.overall`, `stop_flags`) с проверкой схемой; не прошедшие проверку файлы не записываются и возвращаются списком ошибок.
- **Живые обновления:** сервер держит кэш актуальным через `chokidar`, браузер раз в 5 с (когда вкладка видима) опрашивает лёгкий `GET /api/vacancies`. Открытая карточка перезагружается, если её данные изменились на диске; несохранённые заметки при этом не затираются.
- **Фронт:**
  - Вкладки: **«Новые»** (`new`), **«Требуют внимания»** (`needs_attention` + `apply_failed`, с причиной и деталями), **«Выбранные»** (`selected`), **«Все»** (+ фильтр по статусу).
  - Таблица: заголовок, компания, стоп-флаги, регион, дата, overall, бейджи (remote/startup/corporate/outsource/legitimacy), языки, лучший профиль, статус, число дублей. Отмеченные звездой — сверху.
  - Фильтры: поиск по заголовку/компании/локации, минимальный overall, профиль, источник, регион, язык вакансии, дата; сортировка по overall / дате / компании. Фильтры запоминаются в браузере (localStorage).
  - Карточка: summary, key_points, red_flags, частные оценки и обоснование, ссылки (source / real / дубли), особые требования, заметки (сохраняются при потере фокуса), раскрывающийся оригинальный текст. Текст вакансии — чужой контент: сырой HTML экранируется, картинки не загружаются (показываются ссылками), ссылки открываются в новой вкладке.
  - Горячие клавиши: `a` — откликнуться (`selected`), `x` — отклонить, `s` — звезда, `u` — вернуть в `new`, `j`/`k` (↓/↑) — следующая/предыдущая, `/` — поиск. После смены статуса выделение переходит к соседней вакансии.
- **Проверка типов:** `npm run typecheck` проверяет скрипты и `.ts`-код UI (через tsconfig, сгенерированные `nuxi prepare`). Файлы `.vue` пока не проверяются: `vue-tsc` несовместим с TypeScript 7.

## 7. Этап 3 — Отклик («откликнись»)

### 7.1. Команды

| Фраза | Набор вакансий |
|---|---|
| «откликнись» | `selected` **∪** (`new` и `overall ≥ APPLY_SCORE_THRESHOLD`) |
| «откликнись выбранным» | только `selected` |
| «откликнись по скорингу» | только по порогу |
| «откликнись на проблемные» | `needs_attention` + `apply_failed` — повторный прогон с обновлёнными `answers.md` / медиа |

### 7.2. Алгоритм (`playbooks/apply.md`)

1. Сформировать список (исключить `possibly_closed`, учесть `APPLY_MAX_PER_RUN` и `LINKEDIN_APPLY_MAX_PER_DAY`). Вакансии, которые попали в список **только по скорингу** (не `selected` мной), показать и ждать подтверждения (`APPLY_CONFIRM_SCORED=true`). Отмеченные мной `selected` — без подтверждения.
2. **Предпроверка** для каждой вакансии (до открытия формы, если возможно — по тексту вакансии; иначе — открыв форму, но не отправляя):
   - есть ли нестандартные требования (видео/голосовое с конкретным содержанием, тестовое в форме) → `needs_attention: special_media`;
   - можно ли ответить на **все** вопросы формы из `about.md` / `answers.md` → если нет, `needs_attention: unknown_question` с полным текстом вопросов.
   Стандартное «приложите видео-/аудио-визитку» закрывается заготовками из `profile/media/`.
3. Адаптировать резюме и письмо (§7.3), сгенерировать PDF в `data/generated/<id>/`.
4. Открыть `apply_target` (fallback: `real_url` → `source_url`), заполнить форму, приложить файлы, отправить.
5. Записать `status: applied`, `applied_at`, итог в `data/runs/<date>-apply.md` (что отправлено, какие ответы, какое резюме; при возможности — скриншот).
6. Любая ситуация, которую агент не может решить уверенно (капча, логин, странная форма, противоречие), — **остановиться по этой вакансии**, `needs_attention` с описанием, перейти к следующей.

### 7.3. Адаптация резюме и сопроводительного письма (`playbooks/tailor.md`)

- База — `best_resume` из `profile/resumes/`. Агент переставляет акценты, подбирает формулировки и ключевые слова из вакансии, чтобы пройти ATS-фильтры.
- **Граница:** можно переформулировать, переупорядочивать, опускать и подсвечивать то, что **уже есть** в резюме/`about.md`. Нельзя добавлять технологии, годы опыта, должности, проекты, которых нет в исходных данных. Ключевые слова вакансии, которых у меня нет, не вписываются.
- Сопроводительное письмо — по пожеланиям из `profile/cover-letter.md`, на языке вакансии (ru/en/es).
- PDF: `render-resume.ts` (markdown → HTML-шаблон → PDF через Chromium/Playwright). Простая ATS-дружественная вёрстка: один столбец, текстовый слой, без таблиц и картинок.
- Адаптированные версии сохраняются в `data/generated/<id>/` — видно, что именно ушло работодателю.

### 7.4. «Человеческий» темп

- Паузы между вакансиями (`APPLY_DELAY_MIN_SEC`…`APPLY_DELAY_MAX_SEC`, случайные).
- Ввод текста посимвольно с небольшой задержкой (`TYPE_DELAY_MS`) вместо мгновенной вставки значения. Это не гарантия, но убирает самый очевидный сигнал (поле заполнилось за 0 мс без событий клавиатуры). Подробнее о рисках — §11.

## 8. Скоринг

### 8.1. Принцип

- Агент выставляет **частные** оценки 0–100 с коротким обоснованием (точность до единицы не важна).
- **Итог (`overall`)** считается детерминированно скриптом `score.ts` по весам из `config/weights.yaml`, которые отражают `config/preferences.md` (там я текстом описываю, что для меня важно). Меняю предпочтения → меняю веса → `npm run rescore` пересчитывает всё без LLM.
- `scoring_version` — для пересчёта частных оценок агентом, если поменялась сама методика.

**Стоп-факторы** (обнуляют `overall`, в `weights.yaml`; агент ставит флаги в `stop_flags` с обоснованием):

| Флаг | Условие |
|---|---|
| `office_outside_ar` | офис/гибрид без варианта удалёнки **вне** AMBA (Буэнос-Айрес, Ла-Плата и другие города-спутники) и Мар-дель-Платы. Офис там допустим и не штрафуется. Удалёнка как один из вариантов или «сначала удалённо, потом релокация» — это удалёнка; обязательный переезд до начала работы (даже с помощью в релокации) — флаг |
| `location_restricted` | **обязательная** авторизация на работу / проживание в стране или регионе, куда не входит Аргентина (US only, EU work permit). Если это желательно, но не обязательно, флага нет |
| `nationality_excluded` | явный запрет на кандидатов из Аргентины или с гражданством РФ |
| `ru_corporate` | российская госкомпания, компания с госкапиталом (Газпром, Ростех, РЖД, Росатом и т.п.) или любой российский банк — как нанимающая сторона **или** как конечный клиент аутсорса/аутстафа. Частный российский бизнес (Яндекс, Ozon и т.п.) — не флаг, а минус через `corporate` |
| `inadequate` | неадекватный процесс или требования, которые сильно отталкивают: общий созвон со всеми кандидатами, платное «обучение» или тестовое за деньги, бесплатная многодневная работа как тестовое, явное неуважение к кандидату и т.п. |
| `scam` | `legitimacy < 30` — флаг добавляет `score.ts` автоматически |

Формула: `overall = round(Σ w·v / Σ w)` — взвешенное среднее; для `inverse`-критериев `v = 100 − оценка`; `fit` — максимум по трекам от `fit_tracks[трек]·fit[трек]`; оценки `null` и веса 0 исключаются из числителя и знаменателя. Подробно с примером — `docs/how-it-works.md`.

Не стоп-факторы: **EOR** (Deel, Remote.com и т.п.) и **аутсорс/аутстаф** (в т.ч. на крупного клиента) — допустимы и не штрафуются (вес 0).

### 8.2. Corporate vs аутсорс/аутстаф

Корень проблемы — в аутстафе есть **две** организации: та, с кем я подписываю договор, и конечный клиент. Поэтому три отдельные оценки:

| Оценка | Что оценивает | Пример |
|---|---|---|
| `corporate` | **Нанимающая** сторона (с кем договор) — крупный бизнес, где нужно официальное трудоустройство, присутствие, документы. Крупный бизнес любой страны — высоко (требования к документам и присутствию). Российские госкомпании и банки сверх этого получают стоп-флаг `ru_corporate` | Сбер нанимает напрямую → 100 |
| `outsource` | Нанимающая сторона — аутсорс/аутстаф/body-shop | EPAM-подобная или небольшая аутстаф-контора → 80–100 |
| `end_client_corporate` | Только для аутсорса: крупный ли конечный клиент | аутстаф на проект для банка → 90 |

Тогда «аутстаф, работающий на крупного клиента» = `corporate` низкий (договор с аутстафом), `outsource` высокий, `end_client_corporate` высокий — и это **не** конфликт: веса `outsource` и `end_client_corporate` сейчас 0 (это норм). Исключение — конечный клиент российская госкомпания или банк: стоп-флаг `ru_corporate`. Сама крупная аутсорс-компания (EPAM и т.п.) может получить одновременно высокий `corporate` и высокий `outsource` — это тоже корректно.

### 8.3. Направления (`fit`)

| Трек | Что сюда относится |
|---|---|
| `vue`, `react`, `angular` | фронтенд с явным фреймворком |
| `fullstack` | фронт + бэк с конкретным стеком |
| `ai_engineer` | «Software / AI engineer» — современный фулстек без жёсткой привязки к фреймворку, база — Node.js. Сюда же: JavaScript developer, Node.js developer, а также вакансии, где суть — сеньор делает продукт целиком с AI-агентами и язык вторичен (AI-native / Product / Founding Engineer). Python, Go, Rust — только когда язык вторичен; если язык в заголовке или нужен коммерческий опыт на нём — fit низкий (опыта нет) |

### 8.4. Регион и язык

- `config/regions.yaml` — группы стран работодателя (по стране регистрации нанимающей стороны) с оценкой и списком ISO-кодов. Агент заполняет только факты: `company_country` и `ru_speaking_team`; группу `region` и `scores.region` вычисляет `score.ts` (справочник, а не суждение — так оценки согласованы). Приоритет: Аргентина = русскоязычные (включая хабы релокантов и русскоязычные команды в любой стране) = англоязычные (США, Канада, Австралия, Новая Зеландия) > испаноязычные > Европа (включая Великобританию и Ирландию) > ОАЭ > Азия > прочие; страна не определена (`unknown`) — нейтрально. Регион влияет только на удалёнку: офис/гибрид вне Аргентины отсекается стоп-флагом.
- Мои языки: русский (родной), английский, испанский. `vacancy_language` — язык текста; `work_languages` — язык общения, **только если явно указан**, иначе пусто. Оценка `language` снижается, если требуется язык, которого нет в моём списке.

### 8.5. Журнал наблюдений (`data/insights.md`)

При сборе (обязательный шаг playbook) и отклике агент дописывает в общий журнал то, что может пригодиться для улучшения системы. Формат — по строке на наблюдение, с датой и ссылкой на вакансию:

```markdown
## 2026-11-13
- [gap] Часто требуется Kubernetes (3 вакансии: linkedin-401…, …) — нет в резюме
- [inadequate] «Тестовое — 3 дня работы над реальной задачей без оплаты» (remoteok-12…)
- [question] Новый вопрос формы: «Есть ли у вас налоговый статус monotributista?» (getonbrd-…)
- [scoring] Компания X — аутстаф, хотя в описании выглядит как продуктовая
- [source] hh.ru: фильтр «удалёнка» пропускает гибрид
```

Категории: `gap` (требования, которых нет в резюме), `inadequate` (примеры неадекватного — пополняют список стоп-факторов), `question` (новые вопросы форм → в `answers.md`), `scoring` (ошибки/спорные случаи оценки), `source` (проблемы площадок). Журнал я периодически просматриваю и переношу выводы в `preferences.md`, `answers.md`, резюме и playbooks.

## 11. Риски и решения

- **LinkedIn и блокировки.** Чтение тоже рискованно, но заметно меньше откликов: банят в основном за объёмы и ритм (сотни просмотров подряд, однообразные интервалы), реже — за сам факт. Решения: при сборе — умеренные объёмы (лимит страниц уже есть), паузы между открытием вакансий; при отклике — приоритет откликов **вне LinkedIn** (ATS/сайт компании через `apply_target`). Если у вакансии нет дублей и откликнуться можно только через LinkedIn Easy Apply — помечать отдельно (`apply_method: easy-apply`) и либо откликаться самому, либо агентом в пределах `LINKEDIN_APPLY_MAX_PER_DAY=5` (считается по `applied_at` за текущие сутки; мои ручные отклики не учитываются). Обоснование: живой соискатель делает 5–15 откликов в день, 5 автоматических с паузами в несколько минут — заметно ниже порога, на котором LinkedIn начинает показывать предупреждения; лишнее переносится на следующий день. Первую неделю можно держать 3 и поднимать, если нет предупреждений/капч.
- **Медленный ввод текста.** Помогает против простых эвристик, но основные сигналы детекта — отпечаток автоматизации браузера и поведенческие паттерны за сессию. Orca — реальный браузер с моим профилем, что уже лучше headless-скрейперов. Медленный ввод стоит включить: дёшево, вреда нет.
- **Выдумывание фактов** в резюме/ответах — закрывается границей из §7.3 и правилом «не знаешь — `needs_attention`».
- **Стоимость токенов.** Предфильтр по заголовкам до открытия вакансии, HTML→markdown скриптом, дубли без повторного скоринга, источники с API — без браузера.
- **Разные агенты ведут себя по-разному.** Playbook нейтральный; если что-то специфично для агента — короткий раздел-адаптер в `AGENTS.md`.
- **Юридическая сторона.** ToS LinkedIn и ряда площадок запрещают автоматизацию; для личного использования основной риск — блокировка аккаунта. Принимается осознанно.

## 12. С чего начать: первый источник

Браузер Orca проверен на `remoteok.com`. Для старта рекомендую:

1. **RemoteOK** — публичный JSON (`https://remoteok.com/api`), без авторизации, теги `vue`, `react`, `node`, `ai`; только удалёнка. Идеален для отладки всего конвейера (сбор → скоринг → UI) без браузера и без риска для аккаунтов.
2. Следом:
   - **Get on Board** (getonbrd.com) — Латинская Америка, в т.ч. Аргентина, много испаноязычных вакансий, есть публичный API;
   - **hh.ru** — СНГ/Россия, открытый API поиска вакансий (фильтр «удалённая работа»);
   - **Himalayas / We Work Remotely** — удалёнка, Европа;
   - **Greenhouse / Lever / Ashby** — публичные JSON по каждой компании; полезны как `apply_target` при дублях.
3. **LinkedIn** — только после того, как конвейер стабилен, и с лимитами.

## 14. Принятые решения

- `LINKEDIN_APPLY_MAX_PER_DAY=5` — лимит автоматических откликов агента через LinkedIn.
- Подтверждение списка — только для вакансий, отобранных по скорингу.
- Стоп-факторы — см. §8.1; EOR и аутстаф допустимы.
- `COLLECT_STOP_ON_SEEN=5`.
