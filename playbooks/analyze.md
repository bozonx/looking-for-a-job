# Playbook: анализ журнала («проанализируй журнал»)

Цель — по накопленным данным предложить правки **резюме** и **системы сбора**. Ничего не меняй сам:
только отчёт с предложениями; правки — после согласия пользователя.

Три контура, у каждого свои данные:
- **рынок → резюме** — автоматически: `npm run insights` считает спрос трека по всем вакансиям трека (fit ≥ 50),
  включая недоступные по локации, с равным весом, а пробелы — по текущему тексту резюме. Не анализируй только топ
  по overall: overall зависит от совпадения с резюме, и такой анализ подстраивает резюме под то, на что оно уже похоже;
- **калибровка скоринга** — через пользователя: ⚑ и выборка `npm run calibrate` (`playbooks/flagged.md`);
- **предфильтр** — через пользователя: `npm run prefilter-review` (что отсеяно и не зря ли).

## Данные

| Что | Где |
|---|---|
| Сводка (спрос трека, пробелы резюме, ATS-написания, источники, утечки фильтра) | `npm run insights` (по умолчанию 30 дней; `-- --days N` / `-- --since YYYY-MM-DD`). Сохраняется в `data/runs/<дата>-insights.md` |
| Что отсеял предфильтр | `npm run prefilter-review` → `data/runs/<дата>-prefilter.md` |
| Качественные наблюдения | `data/insights.md` (теги `[filter] [source] [scoring] [resume] [bug]`; старые записи могут иметь `[noise]`, `[none]`) |
| Прошлые отчёты анализа | `data/runs/*-insights.md` — сравни с прошлым: что изменилось после правок |
| Резюме | `profile/resumes/*.md`, банк фактов `profile/facts.md` (чем подтверждать bullets), пет-проекты `profile/projects.md`, профиль — `profile/about.md`, предпочтения — `config/preferences.md` |
| Фильтры | `config/prefilter.yaml`, `config/sources.yaml`, `playbooks/scoring.md` |

## Шаги

1. `npm run validate`. Если в отчёте «Поля v3 заполнены у X из Y» и X заметно меньше Y — сначала предложи
   дозаполнить: `npm run pending -- --upgrade` (см. `playbooks/scoring.md`), иначе обязанности и написания неполные.
   Строка «без рыночных полей: N» — предложи `npm run pending -- --market` (короткий `resume_match` у вакансий
   со стоп-флагом по локации), иначе рынок трека неполный.
   Если много «без resume_match» или неизвестных навыков — сначала скажи об этом:
   статистика по резюме будет неполной. Неизвестные навыки предложи добавить в `config/skills.yaml`.
2. `npm run insights`, прочитай отчёт и `data/insights.md` за период.
3. Трек помечен «⚠ мало данных» (< 20 вакансий) — так и скажи; выводы по нему предварительные.
   Навык/формулировку, встретившуюся в 1–2 вакансиях, в резюме не тащи: это специфика компании, а не рынок.
4. **Резюме** — для каждого трека (применение — `playbooks/resume-update.md`, «обнови заготовки резюме»):
   - навыки из «не хватает (обязательные)» с долей ≥ 20% или большим весом: если опыт есть, но не указан —
     **добавить в резюме** (укажи раздел и формулировку); если опыта нет — пометь как **кандидат на изучение**
     и оцени, стоит ли (сколько вакансий, какой у них overall);
   - «ATS: написания навыков» — навык в резюме есть, но написан не так, как чаще пишут вакансии: предложи написание;
   - срез «Что требуют в выбранных вами» — сравни со спросом трека: если выбранные заметно отличаются (другой домен,
     стек), скажи — резюме стоит подстроить под то, куда пользователь реально хочет, а не под средний рынок;
   - «есть в резюме, но вакансия считает минусом» — каждый случай с цитатой; повторяется — предложи убрать/переформулировать;
   - лишнее: навыки, которые в резюме занимают место, но почти не встречаются в `required` трека (см. «спрос»), —
     кандидаты на сокращение;
   - **блок навыков** (порядок): предложи порядок навыков в Skills по «спросу» трека — сначала частые в `required`,
     затем в `nice_to_have`; группировка (Frontend / State / Testing / Infra…). Написание — самое частое из
     «Как пишут навыки»; при заметном разбросе — оба варианта («Vue.js (Vue 3)», «Kubernetes (K8s)»);
   - **bullets опыта**: возьми топ обязанностей трека (доля ≥ 15% или вес в топ-10) и для каждой найди в
     `profile/about.md` / текущем резюме реальный факт, которым её можно подтвердить. Есть — предложи bullet для
     конкретного места работы в формулировке вакансий (глагол + объект + результат/масштаб, если он есть в профиле).
     Нет — отметь «нечем подтвердить» и не придумывай;
   - **summary**: домены и типы продукта из «Контекст» и топ soft-требований — какие из них честно подходят под опыт
     и стоит назвать в summary; медиана лет — сравни с указанным в резюме опытом;
   - сравни треки между собой: может, какой-то трек стоит объединить или вакансий под него почти нет.
   Не предлагай приписать опыт, которого нет. Факт для bullet ищи и в `profile/facts.md`.
   После принятых правок трека — обнови переводы (`playbooks/tailor.md` §2).
5. **Система**:
   - источники с высокой долей `overall<40`/стоп-флагов и малым числом selected/★ (⚑ — см. `data/flagged-cases.md`: повторяющиеся ошибки скоринга → правки `playbooks/scoring.md`) — сузить или отключить;
   - утечки предфильтра — конкретные правила для `config/prefilter.yaml` (`exclude_title` / сужение `include_title`);
     предфильтр с долей отсева ≈ 0% или ≈ 100% — подозрителен;
   - `npm run prefilter-review`: пары «правило против include-ключа», где в примерах есть роли по профилю, и
     «похоже на разработку, но ни одного include-ключа» — пропущенные написания (`forward-deployed` vs `forward deployed`)
     и новые названия ролей; предложи правку `config/prefilter.yaml` с примерами. Мёртвые правила — кандидаты на удаление;
   - повторяющиеся `[scoring]` — правки в `playbooks/scoring.md`; `[bug]` — задачи на исправление;
   - много вакансий без `real_url` при высоком overall — идеи, как находить ссылку автоматически.
6. Отчёт пользователю (по-русски), разделы «Резюме» и «Система»; в каждом пункте — **цифры из отчёта и id примеров**,
   предлагаемая правка и ожидаемый эффект. В конце — топ-3 действия по пользе.
7. Допиши в `data/insights.md` строку `- [analysis] проведён анализ за <период>, отчёт data/runs/<дата>-insights.md`.
