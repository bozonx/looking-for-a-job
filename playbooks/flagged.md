# Playbook: проверь проблемные

Пользователь помечает в UI ⚑ «Проблемная» (`flagged: true`) вакансию, где, по его мнению, что-то не так:
скоринг, данные, вакансия не должна была пройти префильтр и т. п. Причину он обычно пишет в `notes`.
Задача агента — разобрать все ⚑, показать пользователю отчёт с вариантами действий и применить то, что он одобрит.
⚑ защищает вакансию от чистки, поэтому до решения пользователя флаг не снимается.

## 1. Разбор (без правок правил)

1. Список: `grep -rl '^flagged: true' data/vacancies`. Пусто — сообщи и закончи.
2. Для каждой: прочитай `notes`, текст вакансии и поля скоринга. Перепроверь по `playbooks/scoring.md`:
   стоп-флаги, `company_country`, оценки, `resume_match`, `summary`. Если нужно — открой `real_url` (`npm run fetch-page`).
3. Поставь вердикт:
   - `скоринг` — оценки/стоп-флаги/трек не соответствуют `scoring.md`;
   - `правило скоринга` — оценка по правилам верна, но сами правила не учитывают случай;
   - `префильтр` — вакансия не должна была дойти до скоринга (`config/prefilter.yaml`);
   - `данные` — провайдер/парсинг: неверные title, локация, дубль, обрезанный текст, битая ссылка;
   - `не подтвердилось` — всё верно, объясни пользователю почему;
   - `неясно` — причина в `notes` непонятна и сам проблему не находишь.
4. Ошибки данных и явные ошибки скоринга по действующим правилам исправь сразу (это не меняет правил),
   затем `npm run score && npm run validate`. Сомнительное — не меняй.

## 2. Отчёт пользователю

Выведи в чат и сохрани в `data/runs/<YYYY-MM-DD>-flagged.md`:

```
## ⚑ Разбор проблемных — <N> шт.
| # | вакансия | жалоба | вердикт | что сделано | overall до→после |

### Предлагаемые действия
1. [<id>] <конкретное действие> — <зачем>
...
### Системные выводы
- <правка scoring.md / prefilter.yaml / провайдера / источника> — <на каких случаях основано>
```

Варианты действий для каждой вакансии (предлагай подходящие):
- снять ⚑ (вакансия дальше живёт по общим правилам; без ★/статуса/заметки — удалится чисткой);
- снять ⚑ и поставить ★ / отметить на отклик — если после исправления она стала интересной;
- оставить ⚑ и задать вопрос — допиши в `notes` строку `[агент YYYY-MM-DD] <вопрос>`;
- правка правила — дословный текст изменения для `playbooks/scoring.md` или `config/prefilter.yaml`;
- правка провайдера / отключение или сужение источника (`config/sources.yaml`).

Системный вывод предлагай уже по одному случаю, если он однозначен; по нескольким похожим — тем более.

## 3. Применение после ответа пользователя

Пользователь отвечает номерами или «всё». Применяй только одобренное:
- правки правил/префильтра/источников; после правки `prefilter.yaml` или провайдера — `npm run typecheck && npm test`,
  если затронут код; после правки `scoring.md` — перескорь затронутые вакансии;
- снятие ⚑ (`flagged: false`), ★, `status: selected`;
- `npm run score && npm run validate`.

## 4. Журнал

Для каждой разобранной вакансии допиши в конец `data/flagged-cases.md` (файл переживёт удаление вакансии чисткой):
```
## YYYY-MM-DD · <id> · <title> — <company>
- жалоба: <из notes>
- вердикт: <из п. 1.3>
- что было → что стало: <поля и значения; overall до/после>
- системный вывод: <правило или «нет»> · решение пользователя: <принято / отклонено / ждёт>
```
Повторяющийся вывод (≥ 2 случаев в `flagged-cases.md`), который пользователь ещё не принял, — запись `[scoring]`/`[bug]`
в `data/insights.md` с конкретной правкой.

`playbooks/analyze.md` использует `data/flagged-cases.md` как источник типичных ошибок скоринга.
