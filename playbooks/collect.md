# Playbook: сбор вакансий («собери»)

Сбор двухфазный: **скрипт** забирает список, применяет лимиты, предфильтр и дедупликацию → **агент** скорит
только новые вакансии. Так агент не тратит токены на рутину.

1. Прочитай `config/preferences.md`, `config/regions.yaml`, `playbooks/scoring.md`, `config/sources.md`.
2. Запусти `npm run collect` — соберёт все источники со статусом ✅ (один: `npm run collect -- <id>`).
   Скрипт сам: применяет лимиты из `.env` (design.md §5.1), предфильтр (`config/prefilter.yaml`),
   дедупликацию (дубли дописываются в `duplicates` существующей записи, `apply_target` пересчитывается),
   сохраняет новые вакансии со `scores: null` и пишет лог в `data/runs/<дата>-collect.md`.
   Код выхода 1 — у источника не загрузился список (см. «Ошибки» в логе), остальные источники собраны.
   В логе проверь «Дубли … совпадение только по названию»: сравни тексты; если это разные вакансии — сообщи в отчёте.
   «Склеено» — та же роль в другой локации того же источника, проверять не нужно.
   **Код выхода 1 — не перезапускай сбор**: укажи ошибку в отчёте и продолжай с тем, что собрано.
   «⚠ Предупреждения» в логе (например, `COLLECT_MAX_NEW`) — перенеси в отчёт.
   В конце вывода — блок «# ИТОГ СБОРА»: точные цифры и все ошибки/предупреждения по источникам, источник для отчёта (шаг 7).
3. `npm run pending` — очередь на скоринг, не больше `SCORE_MAX_PER_RUN` (свежие первыми). Несвежие (старше `freshness_days`
   источника) не выдаются — их число в конце вывода, перенеси в отчёт; `--stale` — только по просьбе пользователя.
   Скорь **только выданные**; остальные остаются в очереди до следующего «собери». `--all` — только по просьбе пользователя.
4. Для каждой:
   1. Прочитай файл, заполни поля по `playbooks/scoring.md` прямо в front matter
      (тело и остальные поля не трогай). Явно не по профилю — всё равно отскорь (низкий `fit`), не удаляй.
   2. **Реальная ссылка.** Если `real_url: null` или `apply_target` — агрегатор (remoteok, linkedin…), и
      `overall` вероятно будет заметным: найди вакансию на сайте компании / в её ATS (careers-страница,
      `boards.greenhouse.io/<company>`, `jobs.lever.co/<company>`, `jobs.ashbyhq.com/<company>`).
      Нашёл с уверенностью — запиши в `real_url`. Ничего не отправляй. Не нашёл — оставь `null`.
      **Не больше 3 запросов/страниц на вакансию**, затем `null` — не трать токены на поиск.
      `apply_method` и `apply_target` пересчитает `npm run score`.
5. `npm run score` — посчитает `overall`, `scores.region`, `apply_target`; `npm run validate` — исправь ошибки.
   Затем `npm run check-alive` — проверит по real_url, не закрыты ли вакансии (new/selected/needs_attention;
   закрытые получат `possibly_closed: true` и скроются в UI). Затем `npm run top` — топ-5 отскоренных в этом запуске (для отчёта).
   Не исправилось за 2 попытки — остановись и опиши проблему в отчёте.
6. **Обязательно** допиши наблюдения в `data/insights.md` (создай файл, если нет) — раздел `## <дата>`, строки
   `- [тег] <источник или id>: <наблюдение>`. Навыки и пробелы резюме сюда **не** пиши — они в `resume_match`
   и считаются `npm run insights`. Журнал — про то, что не видно из цифр:
   - `[noise]` — мусор, прошедший предфильтр (пример id и почему мусор);
   - `[filter]` — правило предфильтра, которое пропускает лишнее или отрезает нужное (предложи правку `config/prefilter.yaml`);
   - `[source]` — особенности источника: битые/агрегаторские ссылки, дубли, обрезанные описания, редкие обновления;
   - `[scoring]` — спорная оценка, неясное правило в `playbooks/scoring.md`, повторяющаяся неоднозначность;
   - `[resume]` — качественное наблюдение о резюме, которое не ложится в `resume_match` (например, рынок хочет другую подачу роли);
   - `[bug]` — ошибка или странность скриптов/UI.
   Даже если наблюдений нет — строка `- [none] <источник>: без замечаний`.
7. Отчитайся **строго по шаблону** ниже. Цифры сбора и разделы ошибок/предупреждений бери из блока
   «# ИТОГ СБОРА» в конце вывода `npm run collect`, **дословно**: не пересчитывай, не округляй («15+», «более 1600»),
   не пересказывай. Нельзя утверждать то, чего нет в выводе скриптов (например, «ошибок не было», если в ИТОГЕ они есть).
   Пустой раздел — «нет», раздел не выкидывай.

   ```markdown
   ### Сбор
   <строки «- источников…», «- в лентах…», «- дублей…» из ИТОГА как есть>

   ### Ошибки и предупреждения
   <разделы «Источники с ошибкой загрузки», «Ошибки», «⚠ Предупреждения» из ИТОГА как есть; к каждой строке —
   одной фразой, что это значит и нужно ли действие пользователя (баг скрипта → дублируй в insights как [bug])>

   ### Дубли только по названию
   <по каждому: «сверил — та же вакансия» / «разные вакансии: …»; не сверял — так и напиши>

   ### Скоринг
   - <строки «# ИТОГ ОЧЕРЕДИ» из `npm run pending` как есть>
   - <строки «# ИТОГ СКОРИНГА» из `npm run score` как есть>
   - real_url найден: N из M проверенных
   - <строки «# ИТОГ ПРОВЕРКИ» из `npm run check-alive` как есть>
   - `npm run validate`: invalid N, warnings N

   ### Топ-5 по overall
   <вывод `npm run top` как есть — отскоренные в этом запуске; к строке можно добавить одну фразу «почему высоко»>

   ### Требует внимания
   - <стоп-факторы, ручные проверки, спорные оценки; «нет» — если нечего>

   ### Изменённые файлы вне data/
   <`git status --short` без data/ и profile/; ожидается «нет»>
   ```

8. Сохрани отчёт: допиши его в `data/runs/<дата>-report.md` разделом `## <ЧЧ:ММ UTC> — собери`
   (создай файл с заголовком `# <дата> — отчёты`, если нет). Тот же текст — в ответ пользователю.

Строки с `[bug]` в «Ошибках» — баг скрипта (например, коллизия имени файла): обязательно продублируй в
`data/insights.md` как `[bug]` и вынеси в «Требует внимания».

**Во время сбора не правь** `config/*`, `playbooks/*`, `scripts/*`, `profile/*`. Нашёл неизвестный навык, правило предфильтра
или баг — запиши в `data/insights.md` (`[filter]`, `[bug]`, …) как предложение; правки — через «проанализируй журнал»
(`playbooks/analyze.md`) с согласия пользователя.
